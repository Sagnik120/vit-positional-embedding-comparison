# 03 — Deliverables (Exactly What Must Be Produced, And Where)

> Read `01_problem_statement.md` first. Every deliverable below is
> mandatory — none are optional, none can be summarized away, none can
> be replaced with a plausible-sounding placeholder. Every number and
> every plot must come from an actual completed training run.

## RAW DELIVERABLES LIST (verbatim, exactly as given by the instructor)

```
* Top-1 test accuracy for both variants of the trained models (original vs. modified).
* Training/validation loss curves for both, on one plot.
* A short (≤1 page) written justification: why did you choose this alternative
  scheme, and what did you expect it to do differently?
* A short (≤1 page) discussion: did your results match your expectation?
* Full codebases of original ViT and modified ViT with line numbers. A separate
  readme file must be added to indicate the changes you have made (with line
  numbers) in the modified ViT compared to the original ViT.
```

## Deliverable 1 — Top-1 test accuracy, both variants

**What it means:** After training, run each model on the CIFAR-10 **test
set** (10,000 images, never used in training or validation). Top-1
accuracy = percentage of test images where the model's single
highest-probability prediction matches the true label. One number per
variant.

**Where it must exist in this repo:**
- `results/baseline/metrics/test_accuracy.json` — original ViT's number
  (produced by `python -m common.evaluate --model original`)
- `results/modified_rope/metrics/test_accuracy.json` — modified ViT's number
- `results/comparison/top1_test_accuracy_comparison.json` — both numbers
  side by side plus the delta (produced by `scripts/evaluate_all.py`)
- `results/comparison/comparison_table.md` — human-readable table version

**Must use:** each variant's own **best-validation-accuracy checkpoint**
(`checkpoints/best.pt`), never the last-epoch weights, since the task
says "train... to optimize the respective validation performance."

**Do not:**
- Report a training-set or validation-set accuracy in place of test
  accuracy for this deliverable.
- Average or cherry-pick across multiple runs unless multiple full runs
  were actually executed and this is disclosed.
- Round or approximate — use the actual computed value from
  `common/evaluate.py`.

## Deliverable 2 — Training/validation loss curves, both variants, ONE plot

**What it means:** A single plot containing four lines: original-train-loss,
original-val-loss, modified-train-loss, modified-val-loss — all against
epoch number, all on the same axes, so the two variants can be visually
compared directly.

**Where it must exist in this repo:**
- `results/comparison/combined_loss_curves.png` (generated by
  `scripts/evaluate_all.py::plot_combined_loss()`)
- Underlying per-epoch data comes from
  `results/baseline/logs/train_log.csv` and
  `results/modified_rope/logs/train_log.csv`

**Must show:** enough epochs to see the shape of both curves, including
where/if validation loss starts increasing (the overfitting-onset point) —
do not truncate the plot to only the "good-looking" early epochs.

**Extra visualizations that support (but do not replace) this deliverable**
— useful for the analysis in Deliverable 4, save alongside it:
- `results/comparison/combined_accuracy_curves.png` — same idea for
  train/val accuracy (already implemented)
- `results/comparison/generalization_gap_comparison.csv` — train_acc −
  val_acc at each variant's best epoch (already implemented)
- Optionally, per-variant loss-curve-only images already have a home at
  `results/baseline/visualizations/loss_curves/` and
  `results/modified_rope/visualizations/loss_curves/` if a per-variant
  version is useful for the write-up, but the **combined one-plot version
  in `results/comparison/` is the actual required deliverable** — the
  per-variant folders are supplementary, not a substitute.

**Do not:**
- Submit two separate plots (one per variant) as if that satisfies "on
  one plot" — it does not.
- Only plot loss without also being able to reference accuracy/gap
  metrics in the discussion — keep the supporting CSV/plots available.

## Deliverable 3 — Written justification (≤1 page)

**What it means:** A short, focused piece of writing answering exactly
two questions:
1. Why was this specific alternative positional embedding scheme chosen?
2. What behavior difference was expected from it, and why?

**Where it must exist in this repo:** `report/justification.md`

**Content requirements:**
- Must explain *mechanistically* how the chosen scheme (RoPE) differs from
  the original ViT's learned additive PE — not just "it's newer" or "it's
  used in other models."
- Must explicitly address why it is NOT one of the paper's own Appendix D.4
  ablations reworded (hard constraint #1 in `01_problem_statement.md`).
- Must state a concrete, falsifiable expectation (e.g. "expected smaller
  generalization gap," "expected faster convergence") — not a vague claim
  like "expected it to work better" with no specifics, since Deliverable 4
  needs something concrete to check the results against.
- **≤1 page.** This is a hard length constraint — if the draft in
  `report/justification.md` grows beyond roughly 500–600 words / one
  printed page, trim it. Do not pad it with paper background that's
  already in `docs/`.

**Do not:**
- Turn this into a literature review of every RoPE paper ever written —
  keep it focused on this specific comparison.
- State an expectation that isn't checked in the discussion doc — every
  claim made here must be revisited in Deliverable 4.

## Deliverable 4 — Written discussion (≤1 page)

**What it means:** After both models are actually trained and evaluated,
write a short piece answering: did the actual results match the
expectation stated in Deliverable 3?

**Where it must exist in this repo:** `report/discussion.md`

**Content requirements (all must be addressed using REAL numbers, not
placeholders):**
1. State the actual Top-1 test accuracy delta between variants.
2. State the actual generalization-gap comparison (train_acc − val_acc at
   each variant's best epoch).
3. Describe what the actual combined loss curve plot shows — did one
   variant's validation loss inflect upward earlier than the other's?
   Did one converge faster?
4. Explicitly say whether this matches, partially matches, or contradicts
   the expectation written in `report/justification.md` — and if it
   doesn't match, give the most plausible reason why (e.g. small dataset,
   small model, single-run variance), without overclaiming statistical
   significance from a single training run.
5. **≤1 page**, same hard constraint as Deliverable 3.

**Do not:**
- Write this before training has actually finished and real numbers
  exist — a discussion section written from imagined/expected numbers is
  fabrication and violates the "no fabricated results" rule in
  `01_problem_statement.md`.
- Claim a difference is "significant" or "conclusive" from one training
  run per variant — be honest about what a single run can and cannot show.

## Deliverable 5 — Full codebases with line numbers + changes README

**What it means:** Both the original ViT's and the modified ViT's complete
source code must be present, readable, and referenced by line number
where relevant. A separate document must precisely list every change made
in the modified version relative to the original, by line number.

**Where it must exist in this repo:**
- `src/vit_original/vit.py` — the original ViT, complete, unmodified
  (copied from the existing `lucidrains/vit-pytorch` implementation)
- `src/vit_modified/vit.py` — the modified ViT, complete, with the RoPE
  positional embedding mechanism
- `src/vit_modified/positional_embeddings.py` — the RoPE implementation
  itself (new file, has no counterpart in the original — must be
  referenced, not omitted, since it's part of "full codebase of modified
  ViT")
- `CHANGES.md` — the separate changes document, with a line-number diff
  table (original line X ↔ modified line Y, with a one-line description
  of each change: ADDED / REMOVED / CHANGED)

**Content requirements for `CHANGES.md` specifically:**
- Every single functional difference between the two `vit.py` files must
  appear in the table, with accurate, currently-correct line numbers (if
  the underlying `vit.py` is ever replaced/updated, regenerate this table
  — stale line numbers make this deliverable incorrect even if the prose
  is still accurate).
- Must reference `positional_embeddings.py` as a new supporting file, not
  just the diff within `vit.py` itself.
- Must state the parameter-count effect of the change (RoPE adds ~0
  trainable parameters) since this is directly relevant to "everything
  else must be identical."

**Do not:**
- Let `CHANGES.md`'s line numbers drift out of sync with the actual files
  after any edit to either `vit.py` — this must be regenerated any time
  either file changes (see Job 1, step 4 in `02_agent_tasks.md`).
- Bury the diff in prose only — a scannable line-number table is required,
  not just a paragraph description.
- Include changes in `CHANGES.md` that aren't actually about the
  positional embedding mechanism — if `CHANGES.md` reveals an
  architectural difference beyond PE, that's a violation of the "everything
  else identical" constraint, not just a documentation issue, and must be
  fixed in the code, not merely footnoted.
